# Stack-features schema (v0.1)

> **Status**: schema definition only. No per-stack data is populated yet.
> This document defines the columns that `derived/stack_features.{csv,json}`
> will carry once annotation begins. The annotation is **manual**: each
> feature must be reviewed and recorded by a human, with a provenance
> triplet attached. See §5 for the pilot stacks targeted for v0.1.

## 1. Purpose and role in the three-layer structure

The project's three-layer structure separates **evidence**, **derived
metrics**, and **evaluation**:

| Layer | What lives there | Provenance model |
| --- | --- | --- |
| Evidence | `events/*.yaml` — raw event records with primary sources | multi-source admission, body_hash, wayback |
| Derived | `derived/event_metrics.*`, `derived/event_archetypes.*`, `derived/layer_observability.*` | pure function of the evidence layer; regenerated by script |
| **Evaluation** (this doc) | `derived/stack_features.*` + `derived/evaluation_profile.*` | **manual annotation** of stack architectures + rubric mapping |

This file specifies the *stack-features* component: static architectural
and governance features per crypto stack. It is **not** derived from
events — it is coded against public documentation of the stack itself,
then composed with the event-derived archetype frequencies to produce
an exposure profile (see [`evaluation-profile-schema.md`](evaluation-profile-schema.md)).

## 2. Unit of analysis: "stack", not "chain"

The evidence layer has demonstrated empirically that chokepoints in
observed cascades live at the **upper layers** (L4 frontend, asset
on-chain, off-ramp CEX) — see `derived/layer_observability.csv`. Evaluating
"Ethereum" or "Bitcoin" as a single object therefore discards precisely
the signal the data carries. We evaluate **stacks** — tuples of (base
chain, asset rail, frontend profile, access profile, off-ramp profile)
— so the evaluation can reflect which *surface* of a stack is exposed.

Each row in `stack_features.csv` = **one stack snapshot at one timestamp**.

## 3. Provenance triplet (mandatory per-field)

Every architectural or measurement feature on a stack carries three
provenance fields:

| Field | Meaning |
| --- | --- |
| `measured_at` | ISO-8601 date on which the feature value was recorded |
| `measurement_source` | primary / semi-primary reference (URL or body_hash of a dashboard / registry / docs page) |
| `confidence` | `high` / `medium` / `low` — reviewer's self-reported confidence; `low` disqualifies the feature from evaluation-level use |

Features that cannot satisfy this triplet (e.g., self-reported
undocumented governance claims) should be omitted, not guessed. This
rule is analogous to the admission rule in the evidence layer.

## 4. Features (v0.1)

The schema is split into four families. Families reflect the layer-
observability finding: **upper-layer features get fine-grained resolution;
base-layer features get minimal coverage** (they exist so absence of
observation is not confused with absence of feature).

Every feature is either:
- **binary** — `true` / `false`
- **ordinal** — `low` / `medium` / `high` / `n/a`
- **enum** — specific controlled vocabulary (listed inline)
- **numeric** — a continuous or count value with explicit units

All feature values are **static architectural facts at `measured_at`**.
Features that require ongoing measurement (e.g. relay censorship share)
live in the evidence layer, not here.

### 4.1 Frontend-control family (fine-grained)

These are the single highest-information family given `asset_onchain`
and `l4_frontend` together account for most observed cascade activity.

| Feature | Type | Notes |
| --- | --- | --- |
| `canonical_frontend_dependency` | ordinal | high = single operator-hosted domain is the dominant UI (e.g. app.uniswap.org); low = frontend is reproducibly self-hostable and mirrored |
| `canonical_frontend_domain_count` | numeric | count of canonical / near-canonical domains |
| `frontend_operator_jurisdiction` | enum | `US` / `EU` / `UK` / `offshore` / `global_distributed` / `unknown` |
| `dns_domain_chokepoint_dependency` | ordinal | high = operator-controlled apex DNS record is a single point of failure |
| `frontend_geofence_observed` | binary | has this stack's frontend been observed to geofence US / sanctioned users at any `measured_at` point? |
| `client_requires_operator_backend` | binary | does the UI depend on an operator-hosted indexer / server for basic function? |

### 4.2 Asset-control family (fine-grained)

This is the second highest-information family — `asset_onchain` shows
the highest measured conditional change rate (100% of measured events).

| Feature | Type | Notes |
| --- | --- | --- |
| `primary_asset_admin_scope` | enum | set-valued, any of `{freeze, pause, upgrade, mint, burn}`; `none` if no admin authority exists |
| `primary_asset_admin_jurisdiction` | enum | `US` / `EU` / `BVI` / `offshore` / `distributed` / `unknown` |
| `issuer_freeze_power` | ordinal | high = issuer can unilaterally freeze arbitrary address balances on-chain |
| `freezeable_asset_dependency` | ordinal | high = stack's economic activity depends on centrally-controlled assets (USDC/USDT class) |
| `asset_is_upgradeable` | binary | is the asset contract upgradeable by admin or proxy? |
| `native_asset_is_permissionless` | binary | does the stack have a native asset with no admin freeze power (BTC, ETH, SOL base) |
| `alternative_assets_available` | ordinal | low / medium / high — presence of alternative, admin-free units of account in the same stack |

### 4.3 Off-ramp and access family (fine-grained)

Covers `offramp_cex` (64% conditional change when measured) and the L3
RPC access surface.

| Feature | Type | Notes |
| --- | --- | --- |
| `cex_exit_dependency` | ordinal | high = fiat exit is overwhelmingly via KYCed custodial exchanges |
| `dex_exit_feasibility` | ordinal | can a meaningful fraction of users exit the stack without going through a centralised off-ramp? |
| `public_rpc_provider_concentration` | ordinal | high = top-3 providers serve majority of public RPC traffic (Infura-class) |
| `rpc_self_hosting_feasibility` | ordinal | low / medium / high — can end-users or app operators self-host without practical barrier? |
| `primary_fiat_onramp_jurisdiction` | enum | same enum as `frontend_operator_jurisdiction` |

### 4.4 Base-layer / consensus family (minimal coverage)

Kept deliberately thin in v0.1 given layer observability: L0/L1 features
are defined so absence of observation is not mistaken for absence of
feature, but they do not drive evaluation dimensions in v0.1.

| Feature | Type | Notes |
| --- | --- | --- |
| `consensus_model` | enum | `PoW` / `PoS` / `PoA` / `BFT` / `other` |
| `validator_count_order` | enum | order-of-magnitude: `<100` / `100-1k` / `>1k` |
| `validator_jurisdiction_concentration` | ordinal | high = top-3 known-jurisdiction validators > 50% |
| `relay_dependency` | ordinal | high = block production depends on a small set of relays (Ethereum PBS post-Merge) |
| `upgradeability` | enum | `hard_fork_only` / `bip9_miner_vote` / `onchain_governance` / `admin_key` |
| `admin_key_presence` | binary | does any single key / multisig have contract-level upgrade power on the base chain? |

### 4.5 Cross-cutting / governance family

| Feature | Type | Notes |
| --- | --- | --- |
| `governance_centralization` | ordinal | degree to which protocol changes route through a single foundation, committee, or admin key |
| `privacy_technology_presence` | enum | set-valued: `none` / `mixer` / `zk_shielded` / `confidential_tx` / `coinjoin` |
| `jurisdiction_redundancy` | ordinal | different from concentration: does the stack depend on operators in *multiple* sovereign jurisdictions? (low = single-jurisdiction SPOF) |
| `kyc_requirement_level_access` | enum | `none` / `partial` / `mandatory` — coarse grade for the access surface (frontend + RPC + off-ramp combined) |

## 5. Pilot stacks (v0.1)

Five stacks to annotate in v0.1. Chosen to span the strongest
empirical signal from the event panel (upper-layer cascades across
frontend / asset / CEX) while also exercising the coverage-gap families
(privacy tools, base-layer-dominant use). Pick these **before** coding
features so the schema proves itself on the intended targets.

| # | Stack | Rationale |
| --- | --- | --- |
| 1 | `eth_usdc_uniswap_cex` | Ethereum + USDC/USDT + Uniswap-class frontend + major CEX — covers the densest event-evidence corpus (all three upper layers observed) |
| 2 | `tron_usdt` | TRON + USDT — distinct asset-admin jurisdiction and a different frontend / access profile |
| 3 | `privacy_tool_stack` | Tornado Cash / Monero / Zcash (cluster) — heaviest representation in the event panel (8 / 53), exercises the privacy_technology_presence feature and the cross-cutting family |
| 4 | `btc_base_stack` | Bitcoin base-layer-dominant — exercises the minimal-coverage base-layer family, and is the comparison case where the upper layers (frontend, issuer) are less load-bearing |
| 5 | `frontend_mediated_defi_stack` | Aave / Compound / Curve cluster — distinct from the Uniswap stack on frontend admin-key profile and governance centralization |

Each pilot gets one row in `derived/stack_features.csv` with `stack_id`
set to the slug above and `measured_at` set to the annotation date. A
sixth row for Solana is deferred to v0.3.0 (evidence-layer coverage is
too thin to anchor against today — see README §7).

## 6. What this schema explicitly does NOT do

- **No numeric exposure score.** The schema provides features; the
  evaluation profile ([`evaluation-profile-schema.md`](evaluation-profile-schema.md)) maps features
  to ordinal profile dimensions. A single composite score is explicitly
  out of scope for v0.1.
- **No predictive claim.** Features are architectural facts, not
  behavioural predictions. See `docs/limitations-and-use.md` for the
  phrasing discipline.
- **No "chain ranking".** The unit of analysis is the stack, not the
  chain. A stack evaluation does not imply a chain evaluation.
- **No backdating.** `measured_at` is always the annotation date, never
  back-projected. If a historical architectural state is of interest,
  record it as a separate row with a different `measured_at`.

## 7. Revision cadence

Stack architectures move. The intention:
- **v0.1** — 5 pilot stacks annotated with `measured_at` at annotation time
- **v0.2** — quarterly re-annotation; new rows with new `measured_at`
- **v0.3+** — extend to non-pilot stacks as event evidence grows

Revisions are append-only: old rows stay in the CSV with their original
`measured_at`; superseded rows get `superseded_by: {row_id_of_replacement}`
rather than being edited in place. This preserves the timeline that the
evaluation profile will cite against.
